# The Field — controlling product specification

Version: 2026-09-12. Status: accepted product decisions plus explicitly marked implementation defaults. This specification governs the complete intended product, not just the initial code drop. An implemented starter is not approval to reduce version-1 scope. Subsequent explicit user decisions override this document.

## 1. Product and release boundary

The Field prepares CCST-level learners for the CCNA and practical network-support work at a fictional fiber ISP, eventually progressing into engineering. Certification study and career are complete, separately navigable paths sharing skill evidence. Full skill completion requires fresh knowledge evidence and practical demonstrations. Recommended paths permit free exploration; beyond-level material shows prerequisites without blocking a cleared learner.

Version 1 serves up to 10 invited learners on iPhone/iPad and Android phones/tablets, with portrait and landscape support and home-screen installation. Desktop should remain usable. It contains the complete supported CCNA learning path and a career from field technician through introductory network engineering. Environments include residential, small-business, and larger business/campus sites. After promotions, ongoing incidents and expansion projects continue. CCNP-level enterprise and service-provider branches are planned for later releases, sharing foundations; users may select a primary branch, switch, or add the other while preserving applicable qualifications.

The group begins testing only after all version-1 features are complete. Owner review and automated developer verification happen during implementation. The owner delegates routine technical defaults, numerical tuning, and low-value edge cases to the architect. Where compatible capabilities can coexist, implement both rather than returning to an either/or interview. Do not reopen accepted choices needlessly.

Hosting: public GitHub source and Cloudflare Pages. Aim for free services; flag anything requiring payment before provisioning it. No paid AI dependency, background music subscription, automatic upgrade, or required purchased domain. Static hosting alone does not implement secure multi-user identity and synchronization.

## 2. Core presentation and startup

Fresh launch: entirely black page with a blinking white block cursor, no visible title, hostname, prompt, navigation, or button. Tap supports the phone keyboard. Typing `enable` and submitting opens a terminal-style initialization sequence, followed by the current account/gate state or Today. This entrance is a stylistic device; lessons correctly teach that real Cisco `enable` enters privileged EXEC, while configuration needs the appropriate configuration mode. Preserve position on brief resume. Default entrance remains enabled, with a skip setting only after onboarding; it never bypasses clearance or authentication.

Default app appearance is dark with restrained cool blue/cyan accents, customizable later. App icon uses a prompt/cursor. Compact navigation includes Today, Study, Career, Crew, Profile and supports other workspaces without consuming phone screen space. Text conversations only. Subtle optional interface/equipment sounds, no background music. Respect reduced motion; show XP gains and a short completion animation. Offer compact/comfortable presentation, independent text sizes, diagram zoom, and tablets with user-selected pane contents. Preserve realistic behavior when simplifying controls for mobile.

Technician avatars use selectable appearance, hair, work clothing, accessories, and stylized 2D characters alongside realistic hardware illustrations. Create the avatar on first Career entry. Tap a location to immediately open its work area. Equipment inspection uses an overlay; detailed work is full-screen. Cable interaction: choose cable, source port, destination port. No precision dragging requirement. Solo ISP has a default name (architect default: Northline Fiber); crews name their ISP.

## 3. Accounts and prerequisite clearance

Only owner and designated app administrators create app invitations. Default link: one signup, seven-day expiry. Email one-time code is default sign-in. Require saving and confirming account-recovery codes during setup. First goal required; additional goals/time allocations later. Private local work remains available offline on an authenticated device until logout. Logout preserves encrypted unsynced work, accessible only after signing into the same account.

The initial prerequisite diagnostic is mandatory, approximately 20 minutes, starting with basic computer/networking knowledge and practical tasks. It is a gate for CCNA learners, not a beginner course. Overall passing threshold: 70%; knowledge contributes 50%, practical 50%. Stronger areas can offset weaker ones. Latest decisions override earlier per-domain failure gates and optional diagnostics. Results shown to learner: pass/fail only. Owner panel: locked status only, not answers, detailed results, or private action history.

Completed failure immediately produces a black screen containing only `you are not ready`. No preparation links, exit button, contact guidance, or automatic retry. The small initial group contacts the owner in person. Only owner can authorize a full fresh reassessment, never grant clearance directly. No other app administrator may reopen access. On a fresh locked launch: enter `enable`, show permission refusal, request the authorization code. The owner issues a learner-specific, locally verifiable signed code with no expiry. Redemption consumes it and persists a not-yet-started reassessment grant. Learner chooses when to begin. Show no detailed prior results.

All timed assessment interruptions hide tasks/questions/answers and pause active time for five minutes cumulative. A longer interrupted prerequisite attempt permits a fresh attempt without owner authorization; a completed failure does not. Passing grants permanent account-level prerequisite clearance. Encrypt account-bound backups and use protected owner signing material; never embed a shared owner secret in public JavaScript. Document the boundary of offline client trust and deferred reconciliation without claiming impossible tamper resistance.

## 4. Daily plan and study experience

Today combines study and career activities. Ask available time at session start; typical 15–30 minutes. Multiple goals receive selected shares of study time. Selected goals guide prioritization with weaknesses and reassessments incorporated. Optional exam date adjusts preparation; if unrealistic, explain the gap and offer more study time, a later date, or keeping the plan. Unfinished plan: continue or fresh plan. Uninteresting activity: swap for another targeting the same skill. All study modes remain directly accessible and connect to field missions.

Unlearned topics support lesson-first and practice-first routes. Choose domains/topics, activity format, difficulty, session length, and feedback or use adaptive practice. Repeated struggle can step down to prerequisite practice, using an explicit per-concept/difficulty rule and a learner override. Accuracy only; no confidence tracking. Missed-concept mixed review is a per-session toggle.

| Mode | Required behavior |
| --- | --- |
| Questions | Scenario summary plus short default explanation; expandable explanation for every correct/incorrect option. Immediate feedback or end-of-session review. |
| Flashcards | Self-check and typed answers. Official cards linked to skills; personal cards kept in separate decks. |
| Fill in the blank | Explicit accepted conceptual equivalents; command responses require valid supported syntax and legitimate abbreviations. |
| Word bank | Construct concepts, commands, or sequences. Needed pieces only early; plausible distractors at higher difficulty. |
| Reference | Searchable commands, definitions, and examples, available in ordinary learning. Context-sensitive CLI help always retains its realistic meaning. |

Lessons and explanations are original educational content, mapped to a versioned official Cisco blueprint and reviewed for correctness. Do not import exam dumps. All supported objectives need adequate coverage; a heading per domain is not curriculum completeness.

## 5. Mastery and certification evidence

Study mastery: fresh assessment, at least 90%; formats and skill-specific time limit shown before start. Immediate fresh retry after failure, optional review. Free question navigation, answer changes, flags. Timeout submits unanswered items as incorrect. Interrupted answers saved, ended attempt review available immediately, new attempt uses fresh items.

Practical mastery: multiple scenarios with different underlying problems; each skill states its required count. Help is allowed while building evidence, but a final fresh solo assessment must combine the skill’s problem types with typed CLI and ordinary CLI help only. No builder, cheat sheet, traffic teaching view, or scenario hints. Appropriate factual colleague information and execution of a correctly specified request are normal job tools. Accepting diagnostic/solution guidance converts the attempt to practice; explain that transition before applying it. Group missions cannot satisfy final personal practical mastery.

Practical checks have time limits based on complexity, the same pause allowance, and mandatory verification/documentation outcomes. Reset starts a new scored variant. An additional outage means loss of required service outside an explicitly authorized maintenance interruption; causing it fails the scored attempt. Offer recovery practice or debrief. Structured documentation allows typed explanations (required in mastery) plus optional notes. Automatically capture findings; learner selects evidence supporting the conclusion. Show job requirements/failure conditions before starting; reveal detailed rubric after. Debrief compares actual actions with one example expert investigation, acknowledging alternate valid solutions.

Current mastery expires after a displayed per-skill interval. Only passing formal reassessment refreshes it. Reassessment begins shorter and expands if weaknesses appear. Preserve earned history and equipment permissions; require refreshed qualifying mastery before the next promotion. Architect starting intervals: 30 days for high-decay operational skills, 60 for conceptual skills, tuned with explicit content metadata.

Mock exams follow the selected certification version’s actual format/rules, independently verified against official sources. Reserved items plus meaningfully fresh variations; reskinning a seen item does not count as fresh. Insufficient unseen validated material means targeted practice until more is available. Full review and an adjustable remediation plan follow. Readiness combines summary and evidence, requiring consistent performance across several fresh mocks for a strong rating; never promise a pass. Learner may opt to count qualifying mock performance toward study mastery only. Confirmed defective items are excluded and affected scores/readiness recalculated, with correction history. New supported blueprint automatically updates the plan and preserves applicable progress, with explicit mapping and in-progress attempt version handling.

## 6. Simulation, scenes, and career

The simulator is a local state machine with command parsing, device modes, connectivity, configurations, verification, event history, and deterministic fault generation. It must evaluate state/outcomes rather than simply accept one scripted answer. Supported capabilities are explicit and versioned. Valid unambiguous abbreviations should work; unsupported commands clearly identify a simulation limitation and supported alternatives. Never imply a simulated terminal executed on a real network.

Devices/interfaces: router/switch CLIs, Windows/Linux terminals, customer router and ONT management, monitoring dashboards, packet-analysis tools. Begin with consistent teaching interfaces and gradually introduce varied realistic equipment layouts/documents. Teach physical tools and safety explicitly early, expecting independent recognition later. Wrong cables/ports/tools can cause plausible consequences. Standard toolkit first, later preparation/selection; forgotten tool allows borrowing, delivery, or a valid alternative. Explain readings early, require interpretation later. Compress operational waits and show simulated time; keep real assessment clocks separate.

Start with complete topology documentation, then incomplete/outdated diagrams. Learner can manually edit documentation or accept evidence-based corrections. Editing a drawing must not silently change physical state. Select devices from topology plus a recent-device switcher. Ordinary packet-flow teaching view offers step/playback, simple view and expandable headers/decisions. Packet tasks progress from supplied captures to collecting/analyzing generated traffic. Personal external-capture import and professional-detail layouts are planned alongside simplified views; unsupported capture formats must be identified accurately. Monitoring gains realistic detection delays and irrelevant alerts at higher difficulty.

Career board permits free assignment choice with recommendations. Friendly realistic coworkers and occasional humor; mentor onboarding/proactivity selectable. Training grants configuration freedom; career applies earned permissions. Advanced tickets can be worked with restricted actions coordinated through authorized humans in group missions or simulated coworkers solo. Successful changes persist and influence later events. Abandon/fail offers recovery work or restoration; record that choice. Seeded challenge work occurs in a separate network but can earn eligible assignment credit.

Solo network conditions evolve while away via deterministic catch-up; service can worsen but absence is never judged as active job performance. On return show full prioritized backlog. Pause a solo assignment’s dependency footprint while unrelated events continue. When leaving ordinary work for study ask pause/continue; an urgent incident causes a dispatcher request to choose whether to switch. Don’t interrupt formal assessments with unrelated career notices.

## 7. Seeds and career credit

Environment and fault both vary. One fault early, interacting faults later; relevant clues early, plausible distractions later. Fault count shown only in guided practice. Replay exact, generate variation, or enter shared seed. Seed identity includes exact seed and scenario version, with generator compatibility and initial-network context. When missing a version, offer matching download online or a labeled compatible variation.

Base credit reflects difficulty, expected effort, responsibilities. Eligible work contributes promotion requirements, XP/levels, and cosmetics. Exact seed/version successful repeats yield 100%, 50%, 25%, then zero, never reset. Prior solution knowledge is allowed if work is independently completed and verified. This credit rule does not lower freshness/diversity requirements for mastery.

`credit = round(base × (1 − min(0.50, assistance)) × repeat_multiplier)`.

Assistance defaults: reference 2% per opening; builder 30% × assisted submitted commands / all submitted commands, including errors/repeats. Editing a builder insertion remains assisted. Normal CLI help is free. Each nudge 2%, diagnostic clue 5%, explicit solution step 10% (architect-selected defaults, delegated by owner). Authorized coworker execution of a correctly specified request is free; diagnostic guidance is charged. Guided onboarding has no assistance penalty. Explain ordinary deductions only in the final debrief. Never subtract previously earned XP. No career credit for custom scenarios or sandbox exploration.

## 8. Promotions and engineering projects

Responsibility/access requires skill mastery, successful assignments, and a promotion assessment. Manager offers eligible promotion, can defer. Assessment is a simulated shift with several tickets and competing priorities. Reconsider assigned priority as evidence changes. Resolve critical incidents; appropriately document/escalate/hand off remaining work. Deadlines use stated exceptions, such as timely appropriate escalation. Coworkers can give factual information and execute correct requests. Failure requires targeted practice, then a shorter fresh shift emphasizing weaknesses while sampling the whole role. Promotion opens a distinct chapter, workspace, and mentor onboarding. Branch changes preserve shared qualifications and enter the first eligible role.

Projects begin from approved designs and progress to design from business requirements. Balance capacity, availability, security, inventory/cost, maintenance windows, impact, and team coordination. Visual design links addressing/equipment/requirements worksheets. Planning, implementation, verification milestones fit 15–30-minute sessions. Budget excess offers revision, phased work, or a justified budget request. Approval begins manager-reviewed and becomes more autonomous with responsibility.

Static design checks and isolated running tests; manual faults and predefined failure tests. Guidance fades with proficiency. Documentation begins templated and becomes assembled from artifacts. Completion includes as-built diagrams, configurations, test evidence, and monitoring/maintenance/recovery handoff. Check completeness and simulate a colleague using it; explicit early feedback evolves to realistic follow-up questions. Export the full simulated project portfolio. Later incidents include both standard faults and consequences of the learner’s actual design choices.

## 9. Crews, shared state, and competition

Any registered user may request a crew, subject to app-admin approval. Multiple crews, separate networks. Owner/designated crew admins manage members/settings. Ordinary shared missions support 2–4 participants, on crew network or host career network. App assigns skill-based roles; any participant may override/authorize takeover within earned permissions, visibly audited. Missing required person: authorized human takeover, then simulated fallback where allowed. Shared completion credit plus separate personal contribution records.

Per device one configuration controller, others inspect. Normal transfer requires approval, checkpoint, handoff note. Any mission activity retains control. Inactivity timeout is crew-set 2–10 minutes, default 5. Disconnection allows 30 seconds reconnection before takeover; preserve applied changes. Returning original controller and current controller both must agree to return control; disagreement/no response leaves current controller. Leaving a mission offers handoff or remaining connected under these same rules. Server owns leases, roles, versions, event ordering, and permission checks.

Disconnected ordinary co-op becomes a local practice copy. On reconnect show shared state; user can propose useful notes/evidence/config changes. Any other teammate with necessary permission may review. Show diff, evidence, conflicts, and a dry run on current shared network. Permit compatible subset only after retesting that subset. Revalidate version and active controller at application; never merge stale config automatically.

Competitions: live/async, individual/team, self-formed teams. Any crew member organizes. Official ranked, custom unranked. Before opening, freeze assistance format, attempts, best/latest ranking rule, equal/open team-size classification with separate rankings, visibility participants/crew, deadline and upload grace. Architect default grace: 24h. Live provisional score and elapsed time. Offline racer continues local timer; deadline ends scored activity, grace only permits upload. No replacement teammate after ranked attempt starts. Team disconnection must preserve authoritative shared events and explicitly distinguish local practice proposals from scored shared work. Reveal solutions/replays only after close+grace; all participants can view detailed attempts then. Defects: fair recalculation with audit or replacement when necessary.

Human text communication is ticket comments and handoff notes only; no general chat or in-app voice. Attach findings, annotated images, configuration/document files. Posted entries immutable; correction links new entry and supersedes original. Acknowledgment optional. All hosting-crew members read mission history. Attachments offline only on request; removed/replaced cached copy asks whether to retain on reconnect.

Departure: retain completed participated missions as a departure snapshot, no new activity. Shared custom versions persist with attribution. Owner transfers ownership or archives crew. Archive ends unfinished missions, preserves records, offers personal practice copies, no learner failure penalty. Members at archival can browse records/scenarios. Last owner/app admin can reactivate. Restore archived network snapshot; ended attempts remain ended. Restore membership but require confirmation before assigning new work. These archive defaults were delegated by owner.

## 10. Offline storage, content, personal work, and operations

Download the complete released solo curriculum/simulation, not just active missions. Solo lessons, dialogues, seeded generation, practical work, assessments and replay run locally after install. Sync online later. Automatic downloads prefer Wi-Fi with explicit cellular permission; browsers unable to identify connection type must not claim they can reliably enforce it. User storage budget evicts old optional content/cache before core or unsynced work; surface insufficient space and never silently destroy progress. Notifications cannot pretend the browser runs arbitrary background simulation offline.

One device edits a solo attempt. Another resumes last synced state only after explicit takeover; old device’s later work becomes a recovery copy. Every mutation has idempotency/version metadata for sync. Complete offline backups include installed content, encrypted to the creating account. Preview replacement/merge; newer conflicting notes/cards active, older archived. Recovery codes restore account/backup access under a defined key design. Crew owners/admins can include restorable crew backups; verify current permission, pause affected work, notify participants, then restore. Reminders after major milestones/unsynced work.

Private notes attach to topics/questions/missions. Bookmark questions/explanations, commands/definitions, missions/replays/findings. Personal flashcards manual or editable copies; separate personal decks. Individual notes/items/decks shareable to crews. Shared deck owner alone edits, viewers see latest synced version. Copies permitted with attribution and independent editing. Source corrections update untouched copied text, preserve edited text. Import CSV/TSV/XLSX and supported common flashcard formats with explicit capability limits; do not pretend unsupported media/scheduling is imported.

Owner/admin in-app editor for lessons/questions/scenario rules. Learner simple fixed template editor and advanced seeded builder; all creator crews can access after automated validation; custom always practice-only. Fork with permanent origin attribution. Author demonstrates a working solution; engine proposes outcome checks; creator may accept/remove checks. Keep meaningful achievable outcomes and recognize alternative valid solutions. Creator chooses solution reveal rule, displayed before starting. Releases collect drafts, validate, owner alone publishes. Other admins draft only. Offer compatible migration or finish original version. Bug report captures seed/version/relevant history, with offline queue and privacy boundaries.

Progress shows summary plus knowledge and career views. Cosmetics unlock automatically at levels/promotions/skill milestones: badges, titles, avatar items, terminal themes, accents. Equipped rewards and full earned collection visible to crewmates by default; other individual study progress private unless shared.

Notifications offered after meaningful use: study reminders/reassessments, crew invitations/handoffs/action requests, career incidents/network changes. Bundle routine events, deliver time-sensitive requests separately. Quiet hours silence study/career but allow direct crew requests. Respect OS permission and supported PWA APIs. Quota exhaustion keeps local solo usable, indicates unavailable online actions, notifies admin of actual usage/upgrade options, and never enables paid services automatically.

## 11. Implementation boundaries and acceptance discipline

Use a dependency-light static PWA, deterministic pure simulator, structured versioned content, IndexedDB persistence, service-worker release cache, and explicit provider adapters for online features. Never put tokens, signing private keys, real learner data, or production configurations in the public repository. Validate schemas, output escaping, permission boundaries, attachment handling, concurrency, interrupted persistence, and stale evidence. The public source/offline client is not a tamper-proof exam proctor.

Current implementation status and evidence are in IMPLEMENTATION.md; do not infer completeness from this specification. Native device install, keyboard, storage, background interruption, and screen-reader checks must pass on real target devices before group testing. The deployed app’s prerequisites/content/promotion claims must be backed by reviewed content and tests. Keep explicit limitations at the point encountered, without filling learner workflows with irrelevant implementation details.
